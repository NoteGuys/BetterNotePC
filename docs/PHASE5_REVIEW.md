# เฟส 5: ลดงานซ้ำและจำกัดข้อมูลที่หน้าจอต้องถือไว้

วันที่ 8 ตุลาคม 2026 · ฐานก่อนแก้ a643393 บน sol-work

## สถานะ

**งานพัฒนาเฟส 5.1–5.5 และชุดตรวจอัตโนมัติครบตามขอบเขตแล้ว** รวม PDF แบบเตรียมภาพเล็กทุกหน้าและสร้างภาพละเอียดเฉพาะเมื่อใช้ รอผู้ใช้ลอง PDF/อุปกรณ์จริง ส่วนก่อนหน้าเซฟใน a1730d9 แล้ว งานต่อยอด 5.4 รอบนี้ยังไม่ commit/push รายงานนี้ไม่ใช้รับรองว่าไม่มี lag/บั๊กบนทุกเครื่อง

## ผลที่ผู้ใช้ได้

- สมุดยาวไม่ต้องถือรอยเขียน รูปภาพ และพื้นหลังทุกหน้าใน React state ตลอดเวลาที่เปิดสมุด การเลื่อนยังคงกรอบและขนาดของทุกหน้า
- ภาพย่อแสดงเนื้อหาครบทั้งพื้นหลัง PDF ลายมือ ภาพ และข้อความ งานภาพย่ออยู่ใน worker และคิวหยุดเริ่มงานเมื่อกำลังเขียน/ลาก/กดค้าง เก็บ PNG เล็กในฐานแคชแยกหลังเซฟหน้าแล้ว ไม่แก้ข้อมูลโน้ตทุกครั้งที่สร้างภาพ
- อ่านไม่สำเร็จจะแสดงโหลด/ลองใหม่ ไม่เปิดหน้าสรุป metadata ให้เขียนเป็นหน้าว่าง
- Undo/Redo ติดดาว เปลี่ยนพื้นหลัง คัดลอกหน้า แทรกภาพ และการส่งออก ใช้เนื้อหาจริงก่อนเปลี่ยนข้อมูล ไม่บันทึก placeholder ทับหน้าจริง
- ส่งออก .bnote รอคิวเซฟแล้วใช้ snapshot และเข้ารหัส JSON ใน worker; PDF/ภาพหน้าเดียวต้องโหลดหน้านั้นครบก่อน ส่วน PDF ทั้งเล่มใน editor อ่านทีละหน้าเฉพาะเมื่อสั่งส่งออก
- PDF ที่นำเข้าใหม่มีข้อมูลต้นฉบับอยู่ในสมุดสำรองหนึ่งชุดต่อแหล่ง PDF ไม่ใส่ต้นฉบับซ้ำทุกหน้า และย้ายเจ้าของต้นฉบับใน transaction เดียวเมื่อหน้าที่ถือไฟล์นั้นถูกลบ
- ปุ่มล้างแคชเดิมล้างภาพย่อจริงแล้วเตรียมภาพของสมุดที่เปิดใหม่ ไม่ลบรอยเขียน ข้อมูลที่รอเซฟ หรือ Undo

## สิ่งที่ตรวจพบระหว่างพัฒนาและแก้แล้ว

- การรอโหลดหน้าทุกครั้งก่อน Undo ทำให้กด Undo ติดกันชนกัน: คงทางเดิมสำหรับหน้าที่โหลดแล้ว และต่อคิวเมื่อจำเป็นต้องโหลด
- การส่งออกหน้าเดียวจาก placeholder อาจได้หน้าว่าง: เพิ่มการโหลดหน้าจริงและหยุดเมื่ออ่าน/เซฟไม่สำเร็จ
- คำสั่งติดดาวที่กดติดกันระหว่างโหลดหน้าอาจอ่านสถานะเดียวกัน: จัดลำดับผ่านคิวเดิม และรักษาการเปลี่ยนสถานะแบบทันทีสำหรับหน้าที่โหลดแล้ว
- Lasso วาดฉบับคัดลอกไว้แล้ว แต่ incremental renderer วาดไฮไลต์เพิ่มซ้ำ: ทำซ้ำด้วยการเทียบ SHA-256 ของพิกเซลจริงก่อนแก้ได้ แก้โดยยกเลิกสถานะ append ทุกจุดที่วาด static layer ด้วยมือ ผลหลังแก้ตรงกับเปิดสมุดใหม่
- timestamp ของหน้าใน UI กับค่าหลัง commit อาจต่างกัน: ภาพย่อรับฉบับฐานข้อมูลที่ใหม่กว่า และใช้ snapshot ในคิวถ้ายังมีงานรอเซฟ ไม่แสดงฉบับเก่าแทนงานที่ยังเซฟไม่ได้
- การซ่อน PDF ต้นฉบับเฉพาะตอนโหลดไม่พอ เพราะการเซฟก็ต้องรักษาไฟล์นั้นด้วย: ย้ายการอ่าน/เขียนหน้าที่แนบต้นฉบับไป worker และคงคิวเซฟ/ลองใหม่เดิม

## หลักฐาน

ใช้ฐานข้อมูลและโปรไฟล์ทดสอบแยก ข้อมูลทั้งหมดสร้างขึ้นเพื่อทดสอบ ไม่อ่านหรือเขียนสมุดจริง ไม่แตะ Drive จริง และปิดคำขอเครือข่ายภายนอกใน browser harness

## ปรับตามผลใช้งาน: ภาพย่อไม่หายเมื่อเลื่อน — 8 ตุลาคม 2026

ผู้ใช้แจ้งว่าส่วนอื่นผ่าน แต่ไม่ต้องการให้ sidebar ค่อย ๆ สร้างภาพเมื่อเลื่อน จึงเปลี่ยนเป็นเก็บภาพย่อแยกจากอายุของหน้าที่โหลด และเตรียมหน้าที่ยังไม่เห็นของสมุดที่เปิดในพื้นหลังด้วย worker ทีละหน้า ไม่เพิ่ม Canvas ของทั้งสมุดเข้า UI

- เปลี่ยนคีย์แคชจากอ้างอิง object เป็น ID สมุด/หน้า/พื้นหลัง/รอบกู้คืน จึงเลื่อนกลับมาใช้ภาพเดิมได้แม้ rich page ถูกคืนหน่วยความจำแล้ว
- เก็บ PNG ที่ยืนยันจากหน้าที่เซฟแล้วใน BetterNote_PagePreviews แยกจากฐานโน้ต; อ่านกลับพร้อมรายการหน้าก่อนแสดง sidebar จึงใช้ได้หลังเปิดสมุดหรือ renderer ใหม่ งานที่เซฟยังไม่สำเร็จไม่เขียนภาพฉบับนั้นลงแคชถาวร
- เมื่อแก้รอยเขียน คงภาพก่อนหน้าไว้ระหว่างอัปเดต ไม่ล้างให้กลายเป็นช่องว่าง; ส่งเพียง summary ให้ worker เมื่ออ่านหน้าจากฐานข้อมูลได้ และหยุดเริ่มงานระหว่างอินพุตใช้งาน
- แคช RAM ไม่เกิน 32 MiB, ดิสก์ไม่เกิน 64 MiB, PNG ไม่เกิน 512 KiB ต่อรายการ และอ่านกลับไม่เกิน 24 MiB ต่อสมุดในครั้งเดียว ภาพ fallback รับเฉพาะ data URL ของภาพเล็ก ไม่โหลด URL ภายนอก
- ใช้ receipt เดิมของการกู้คืนแยกชุดแคช ป้องกันภาพเก่าที่ timestamp ตรงกันค้างหลัง restore; ไม่เปลี่ยนระบบกู้คืน

ตรวจเพิ่ม 7 กรณีจริง: เตรียมครบ 12 หน้าขณะปิด sidebar โดย rich pages ยังจำกัด, เลื่อนไป/กลับมี PNG ตรงตั้งแต่เฟรมที่ตรวจ, แก้รอยเขียนขณะ pen active แล้วยังคงภาพเดิม, คืนจากดิสก์หลังล้างเฉพาะ RAM, เนื้อหา/backup ไม่เปลี่ยน, reload renderer แล้วยังได้ภาพเดิมทันที และ receipt กู้คืนยกเลิกภาพชุดก่อน การทดสอบทั้งหมดใช้ข้อมูลจำลอง

สมุดที่ยังไม่เคยมีภาพย่อหรือเพิ่งล้างแคชยังต้องเตรียมครั้งแรก ไม่มีการหน่วงเปิดสมุดเพื่อบังคับรอครบทั้งเล่ม เมื่อเตรียมแล้วจึงไม่ต้องสร้างซ้ำตอนเลื่อนในขนาดที่แคชรองรับ สมุดใหญ่มากเกินเพดานแคชอาจมีภาพถูกนำออกแล้วต้องเตรียมใหม่ ขอบเขตนี้ไม่ใช่คำรับรองว่าไม่มีเวลารอบนอุปกรณ์หรือสมุดทุกขนาด

## ขอบเขตหน่วยความจำและสิ่งที่ยังเหลือ

แคช 32 MiB จำกัดข้อมูล preview ที่ service ถือ ไม่ใช่ RAM ทั้งแอปหรือหน่วยความจำ decoded images ของเบราว์เซอร์ Canvas ใช้ budget 96 MiB สำหรับสามชั้นหน้าปัจจุบัน และ 12 MiB ต่อหน้าเพื่อนบ้านในแนวตั้ง รวมสูงสุดประมาณ 144 MiB สำหรับ backing stores ของห้าหน้าที่กำหนด ไม่รวมรูปภาพ, DOM, browser overhead, เนื้อหาหน้าเดียวที่ใหญ่มาก, pending saves และ history ที่ยังจำเป็นต่อการรักษางาน

หน้าที่ใหญ่ผิดปกติอาจแสดง bitmap ละเอียดน้อยลงตาม budget แต่ไม่เปลี่ยนพิกัด ขนาดกระดาษ หรือข้อมูลลายเส้นที่บันทึกไว้

PDF ที่นำเข้าใหม่เตรียม JPEG ภาพเล็กทุกหน้าให้พร้อมเลื่อน แล้วสร้างภาพละเอียดเฉพาะเมื่ออ่าน/หน้าใกล้ หรือสั่งส่งออก/สำรองจากต้นฉบับ ไม่เก็บภาพใหญ่ทุกหน้าตอนนำเข้า สมุด PDF เก่าที่มีเพียงภาพใช้ทางเดิมและไม่เขียนทับข้อมูลผู้ใช้ รายละเอียดข้อจำกัด ฟอนต์ ฟิลเตอร์ และหลักฐานอยู่ใน docs/PHASE5_4_REVIEW.md

ไม่มีผลทดสอบที่รับรองว่าไม่ lag หรือไม่มีบั๊กบนทุกเครื่อง ชุดย้ายเครื่องขณะรันหลายชุดพร้อมกันยังวัด heartbeat สะดุดได้ถึงประมาณ 576 ms ดังนั้นรายงานนี้รับรองเฉพาะความถูกต้องที่ชุดตรวจครอบคลุม และการลดงาน/ข้อมูลตามตัวเลขข้างต้น ยังต้องทดสอบไฟล์ใหญ่และอุปกรณ์จริงต่อ

## ไฟล์และการเซฟ

Runtime เปลี่ยนเฉพาะ editor/ภาพย่อ, แคช, การโหลด/เซฟหน้าที่เกี่ยวข้อง และการนำเข้า/ส่งออก PDF/.bnote ไม่มีการแก้ระบบบัญชี OAuth หรือข้อมูลสำรองจริง ไม่มีการเปลี่ยน schema ฐานข้อมูลโน้ต; เพิ่มฐานแคชภาพย่อแยกที่ล้างหรือสร้างใหม่ได้

งานเดิมเซฟและ push ใน a1730d9 แล้ว งานต่อยอด 5.4 รอบนี้ยังไม่ commit/push ต้องแสดงรายการไฟล์ ตรวจไฟล์ลับ/โน้ตสำรอง และรอผู้ใช้ตอบ “ตกลง” ตามขั้นตอนเซฟเกมก่อน ไม่รวม core-js-banners หรือ node-compile-cache/ ที่มีค้างอยู่ก่อนเริ่ม


## ส่งออกทั้งเล่มรอบแบ่งชุด

ผู้ใช้ยังพบปัญหากับสมุดจริงหลังแก้ URL ยาว จึงเปลี่ยนเป็น protocol 2, สร้างทีละชุดและรวมใน worker พร้อมแยกสถานะและข้อผิดพลาด Native 91 หน้าเดิม/นำเข้าใหม่และ 240 หน้า รวมกรณี retry หลังล้มเหลวผ่านแล้ว; PDF browser suite รอบล่าสุด 29 ผ่าน รายละเอียดใน [PDF_EXPORT_REVIEW.md](PDF_EXPORT_REVIEW.md) ยังรอผู้ใช้ยืนยันสมุดจริงและยังไม่ commit/push


แก้รอบ load-document: เข้ารหัส file URL และเทียบพาธไฟล์หลัง decode รองรับ Windows Temp ภาษาไทย พร้อมแก้เลขช่วงหน้าในข้อความ export; unit 193 / PDF suite 30 / native 91 หน้าผ่าน รายละเอียดใน PDF_EXPORT_REVIEW.md ยังรอผลสมุดจริงและยังไม่ commit/push
