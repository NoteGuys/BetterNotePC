# เฟส 3.4 — ทดสอบการย้ายเครื่องครบเส้นทาง

วันที่: 7 ตุลาคม 2026
ฐานโค้ด: `ffd8462` บน `sol-work`
สถานะ: ทดสอบด้านข้อมูล การย้ายเครื่อง และ Drive เสร็จแล้ว; หยุดให้ผู้ใช้ตรวจผล ความลื่นของสมุดใหญ่ยังมีจุดต้องปรับก่อนอ้างว่าไม่ lag

## สิ่งที่ผู้ใช้ได้จากผลตรวจนี้

- ใช้โปรไฟล์ทดสอบใหม่เสมือนเครื่อง A/B/C และอีกโปรไฟล์รับจาก Drive จริง โดยไม่เปิดฐานข้อมูลของ BetterNote ที่ติดตั้งอยู่
- เครื่องใหม่รับสมุดเดิมตาม ID ได้ เนื้อหาเท่ากันเมื่อเทียบ canonical SHA-256 ครบทุกเล่ม ไม่อาศัยเพียงชื่อหรือวันที่
- โฟลเดอร์ซ้อน ชื่อ/สี/parent สมุดชื่อเหมือนกัน ลำดับหน้า หน้าติดดาว สมุดติดดาว รูปล็อก ข้อความ ลายมือ พื้นหลัง PDF ไฟล์ PDF ต้นฉบับ และตำแหน่งติดลบใน whiteboard ผ่าน
- ใช้ App, Library, NoteEditor, Canvas และการนำทางจริง ไม่แทน editor ด้วยหน้าว่าง เขียนเพิ่มด้วย PointerEvent ชนิด pen แล้วตรวจข้อมูลที่เซฟจริง
- ปิด browser/Electron ทั้งโปรเซส เปิดโปรไฟล์เดิมใหม่ แล้วข้อมูลและฐานฉบับร่วมยังอยู่ เขียนต่อและส่งงานกลับเครื่องต้นทางได้
- เมื่อสองเครื่องแก้พร้อมกัน เก็บทั้งฉบับต้นทางและสำเนาฉบับในเครื่อง รหัสหน้าของสำเนาไม่ชน และปิด–เปิดใหม่แล้วสำเนายังอยู่
- Restore จากโฟลเดอร์แบบสั่งเองผ่านด้วย ไม่เปลี่ยนการตั้งค่าปลายทาง Local ของเครื่องรับ
- ไฟล์ที่ต้องใช้หายหรือเสียทำให้ปฏิเสธ Restore/การเขียนร่วม ไม่เอาไฟล์เสียไปแทนสมุดในเครื่อง ไม่ข้ามไปหา backup คนละโฟลเดอร์ Local backup ยังทำงานเมื่อ Drive ถูกกันไว้
- ปิดโปรเซสระหว่างพักการอ่านก่อน commit แล้วเปิดใหม่ ข้อมูลที่ commit ไว้ก่อนหน้ายังอยู่และรับงานต่อได้; การ abort transaction/receipt/intent หลังเขียนบางส่วนมี regression เดิมในชุด unit/native
- การตรวจตอนว่างอ่าน metadata ไม่มีงานเขียนซ้ำ ไม่เรียก `pages.getAll()` และไม่ตั้ง `cloudUploadVerified` เป็นจริงจาก filesystem

## ผลการทดสอบ

| ชุดตรวจ | ผ่าน | หมายเหตุ |
| --- | ---: | --- |
| Unit/native เดิมทั้งหมด ยกเว้นชุดไฟล์ใหญ่ 268 MiB ที่เคยผ่านใน 3.3 | 313 | ไม่สร้าง archive ใหญ่นั้นซ้ำ |
| ย้ายเครื่องด้วยโปรไฟล์ถาวร App/editor จริงและ Drive child ใหม่ | 19 | 17 กรณีหลัก + 2 กรณี Drive mount จริง |
| Electron จริง ใช้เนื้อหา preload เดิม, IPC, native workers และ production recovery worker | 6 | ตรวจสมุดใหญ่ แยกข้อมูล/PDF ปิด–เปิดโปรไฟล์ และ idle |
| รวมกรณีที่ตรวจในรอบนี้ | 338 | ไม่บวกการรันทดสอบข้อเดิมซ้ำ |

หลังปรับ transport ของเครื่องมือทดสอบ browser ให้ไม่แปลง binary เป็นอาร์เรย์หลายล้านสมาชิก ตรวจ 17 ข้อหลักซ้ำผ่าน ทดสอบ Electron เพิ่มเพื่อไม่ใช้ตัวส่งข้อมูลจำลองของ Playwright เป็นหลักฐานความเร็ว IPC

Electron QA คัดลอก preload เดิมทุกไบต์ไปใน QA เท่านั้น ใช้ main bootstrap สำหรับควบคุมปลายทาง ไม่ใช่การเปิดโปรแกรมติดตั้งจริง; แยก userData/sessionData และบล็อกเครือข่าย HTTP(S) ทั้งหมดในตัวแอปจำลอง การแนบ CDP บางครั้งพบ bridge ไม่พร้อมในเอกสารแรก ตัวทดสอบตรวจ capabilities และรีโหลดได้หนึ่งครั้งก่อน seed/run ไม่เปลี่ยน preload หรือการเปิดแอปจริง จึงไม่ได้ใช้ชุดนี้รับรองพฤติกรรม cold-start ของ installer

รอบนี้เพิ่มเฉพาะไฟล์ทดสอบและเอกสาร ไม่มีการแก้ source/runtime ของแอป ไม่มีการบิลด์ใหม่ ใช้ production inline workers จาก build 3.3 ที่ตรวจผ่านแล้ว `git diff --check` ผ่าน

## ความลื่น: ผลที่วัดได้และสิ่งที่ยังเหลือ

สมุดจำลอง Electron มี 24 หน้า 144,000 จุดปากกา JSON ประมาณ 4.49 MiB:

| ขั้นตอน | เวลารวมรอบสุดท้าย | ช่องว่าง heartbeat สูงสุด |
| --- | ---: | ---: |
| รับข้อมูล + เซฟสำรองที่แก้ไขได้ | 1.19 วินาที | 358 ms |
| สร้างและเซฟ PDF หลังยืนยันข้อมูลแล้ว | 5.12 วินาที | 173 ms |

ก่อนติด profiler รอบเดียวกันเคยวัดได้ 1.46 วินาที/350 ms สำหรับข้อมูล และ 5.15 วินาที/401 ms สำหรับ PDF ตัวเลขเป็นผลบนเครื่องนี้ใน QA ไม่ใช่ SLA

**ไม่มีช่วงหยุด heartbeat ยาว 5 วินาทีในการทดสอบ แต่ยังพบสะดุดสั้น จึงยังไม่ผ่านเป้าหมายไม่ lag ทุกจังหวะ** เงื่อนไข assert ของชุด stress ตรวจว่าไม่หยุดยาวและได้ข้อมูลครบ ไม่ใช่เกณฑ์ 60 FPS

CPU profile ชี้ว่ามีต้นทุนในทางส่งสมุดเข้า `window.electronAPI.saveBackup` / `ipcRenderer.invoke`, การอ่าน snapshot ทีละหน้า และ GC; บางส่วนเป็น native/program samples จึงไม่ระบุว่าเป็น IPC เพียงสาเหตุเดียว ส่วน PDF ยังใช้การวาด/เข้ารหัสบน renderer เป็นช่วง ๆ แม้แบ่งระหว่างหน้าแล้ว

แนวทางถัดไปที่อยู่ในขอบเขตสำรอง/ซิงค์:

1. ลดการส่ง object สมุดขนาดใหญ่ผ่าน renderer และ IPC โดยให้ worker อ่าน/เตรียมข้อมูลจาก IndexedDB ส่งเป็น bytes หรือช่วงข้อมูลที่จำกัด พร้อมรักษา snapshot/guard/hash/transaction เดิม
2. ลดงาน PDF อัตโนมัติบน renderer ให้ทำเมื่อว่างหรือใช้ worker ในทางสำรอง โดยไม่แก้การเขียน Canvas/ปากกา/การ export ที่ผู้ใช้กดเอง
3. ทดสอบก่อน–หลังด้วย fixture เดิมและ Electron จริง ใช้เกณฑ์ความลื่นเข้มกว่าการไม่หยุด 5 วินาที พร้อมตรวจข้อมูลและการกู้คืนซ้ำ

ยังไม่ได้ลงมือปรับสามข้อนี้ในรอบทดสอบ เพื่อให้ผู้ใช้ตรวจผลและขอบเขตก่อน ไม่รับรองว่าไม่มีบั๊กในทุกขนาดสมุดหรือทุกสถานการณ์

กำหนด `NODE_DISABLE_COMPILE_CACHE=1`, `BETTERNOTE_QA_TEMP` เป็นพื้นที่ QA แยก, `BETTERNOTE_PLAYWRIGHT_PATH` เป็น Playwright runtime และ `BETTERNOTE_QA_BUILT_WORKER=1` ใช้ Edge ผ่าน `BETTERNOTE_QA_BROWSER` สำหรับ browser test แล้วรัน:

```text
node tests/backup-migration.browser.cjs
node tests/backup-migration-native.browser.cjs
```

`BETTERNOTE_QA_DRIVE_PARENT` เป็นตัวเลือก ต้องตรงพาธที่ผู้ใช้อนุญาตในเซสชันนี้เท่านั้น ตัวทดสอบสร้าง child ใหม่ชื่อ BetterNote-Phase3-Test-* และไม่ทำ recursive cleanup

ยังไม่ commit/push งานรอบนี้ รอขั้นตอนตรวจไฟล์และการตอบ “ตกลง” ของผู้ใช้ ไม่เริ่มเฟสถัดไป
