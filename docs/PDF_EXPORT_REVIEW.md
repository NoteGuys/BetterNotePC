# การแก้ส่งออก PDF ทั้งเล่ม รอบแบ่งชุด — 8 ตุลาคม 2026

ผู้ใช้ยังพบข้อความสร้าง PDF ไม่สำเร็จหลังเตรียมหน้า 91/91 แม้แก้ URL ยาวในรอบก่อนแล้ว ข้อความนั้นซ่อนหลายสาเหตุไว้เหมือนกัน จึงยังไม่ยืนยันว่าข้อผิดพลาดของสมุดจริงเกิดจากหน่วยความจำหรือโปรเซสเก่า การทดสอบจำลองรอบก่อนใช้ยืนยันแทนไฟล์จริงไม่ได้

## ระบบที่ปรับ

- ตรวจ protocol 2 ก่อนอ่านหน้า: หาก main process ยังเป็นรุ่นเก่า แจ้งปิดเปิด BetterNote ใหม่
- ExportModal อ่านจากฐานข้อมูลทีละหน้า หลัง flush การบันทึก โดยไม่ mount หน้าที่ส่งออกใน editor; ต้นฉบับ PDF ของหน้า owner อ่านและตัดออกใน worker
- เตรียม SVG เดิมและภาพละเอียดเดิม ชุดละไม่เกิน 4 หน้า หรือประมาณ 8 MiB ของ HTML; หน้าที่ใหญ่กว่าเพดานชุดส่งเดี่ยว มี hard limit IPC 64 MiB
- สร้าง PDF ผ่าน native printToPDF ใน hidden window ที่เปิด sandbox, ปิด JavaScript และปฏิเสธ network/ไฟล์อื่น
- PDF แต่ละชุดเขียนในโฟลเดอร์ชั่วคราวที่ระบบสร้างเอง จากนั้น pdf-lib 1.17.1 copyPages ใน Node worker คัดลอกหน้า/เวกเตอร์/ฟอนต์/ภาพโดยไม่ render หรือบีบอัดภาพซ้ำ ไม่รับเส้นทางจาก renderer
- ตรวจจำนวนหน้าทุกชุดและก่อนส่งไฟล์สุดท้าย ชุดที่ print/load/timeout ล้มเหลวลองแบ่งครึ่งจนถึงหน้าเดียว; หาก merge อาจเริ่มเปลี่ยนข้อมูลแล้ว จะหยุดและล้าง session ไม่ retry ให้หน้าซ้ำ
- แสดงขั้นเตรียมหน้า/สร้าง PDF/รวมและตรวจ/เตรียมดาวน์โหลด แยกข้อความ read/print/load/temp/merge/count/timeout พร้อมช่วงหน้าที่ล้มเหลวทั้ง 4 ภาษา
- diagnostic JSONL ใน OS temp จำกัดขนาดประมาณ 512 KiB มีเฉพาะ protocol/stage/status/count/bytes/time/reason/memory ไม่เก็บ HTML, ชื่อสมุด, ตำแหน่งไฟล์ หรือ raw error
- session จำกัดหนึ่งงานต่อหน้าต่าง ป้องกัน append ผิดลำดับ ล้าง worker/ไฟล์ชั่วคราวเมื่อเสร็จ ยกเลิก หรือหน้าต่างปิด มี idle cleanup

- Unit 192 ผ่าน; รวม 8 กรณี native export/session/merge/lifecycle/security
- Editor/IndexedDB/UI 159 ผ่าน ไม่มี renderer error
- PDF browser suite 29 ผ่าน รวมการตรวจ main process เก่าก่อนอ่านหน้า การอ่านทีละหน้า ลองชุดเล็กลงและดาวน์โหลดเล่มเดียว การอ่านหน้าขาดแล้วระบุหน้า/ยกเลิกโดยไม่ดาวน์โหลดไฟล์ที่ไม่ครบ
- Production build ผ่าน; ยังมีคำเตือนขนาด chunk เดิม
- Electron native PDF 91 หน้าเดิม ส่งออกทั้งเล่มครั้งแรกสำเร็จ 6,810,379 bytes
- Electron native PDF นำเข้าแบบ lazy 91 หน้า ส่งออกทั้งเล่มครั้งแรกสำเร็จ 46,422,896 bytes ใช้เวลา 14.6 วินาทีใน fixture; ข้อความไทย ภาพ ลายมือ ลำดับและขนาดหน้าครบ
- บังคับ native print ชุดแรกให้ล้มเหลว: retry ชุดเล็กลงสำเร็จครบ 91 หน้า 7,004,577 bytes ใช้เวลา 7.2 วินาที
- สมุดจำลอง 240 หน้า: 18,430,309 bytes ครบ 240 หน้า ใช้เวลา 17.0 วินาที
- ตรวจข้อความหน้าต้น/46/ท้าย แนวตั้ง/นอน พิกเซลพื้นหลังแดง/ลายมือฟ้า และจำนวนหน้าสุดท้าย ทั้ง native cases มี timer ของ renderer เดินต่อ มี progress ทุกขั้น ไม่มี temp directory ของงานหรือ hidden export window ค้าง
- ตัวทดสอบใช้ fixture preload ในหน้าต่าง QA แยก (sandbox false สำหรับ bridge ของ fixture); หน้าต่างสร้าง PDF ของ production module ที่ทดสอบเปิด sandbox true/JavaScript false จริง ไม่ได้เปลี่ยนค่า sandbox ของแอปจริง
- ข้อมูลทั้งหมดสังเคราะห์ใน scratch ไม่มีการเปิดสมุดจริง โปรไฟล์ติดตั้ง Google Drive หรือ OAuth credential

## ข้อจำกัดและสถานะ

การแบ่งชุดจำกัดภาระสร้างภาพ/HTML/DOM แต่ worker รวมไฟล์ยังเก็บ object และ stream ที่บีบอัดของ PDF สุดท้ายใน RAM ตามขนาดไฟล์ ไม่ใช่การรับประกัน RAM คงที่สำหรับทุกสมุด PDF ต้นฉบับถูกใช้สร้างพื้นหลังตามคุณภาพเดิม; การรวมไฟล์ไม่ได้ทำให้ PDF ที่ถูกแปลงเป็นภาพในระบบเดิมกลับมาเป็นข้อความต้นฉบับที่เลือกได้

การ export ที่เรียกจาก Documents โดยส่ง pages ทั้งหมดมาเองยังถือ snapshot เดิม; ทาง ExportModal ใน editor ใช้อ่านทีละหน้าแล้ว

ยังต้องยืนยันสมุดจริง Class 5-6 ของผู้ใช้: ปิด BetterNote ที่ใช้ทดสอบทั้งหมด เปิดใหม่ แล้วส่งออก entire notebook เป็นคำสั่งแรกโดยไม่ส่งออกหน้า 1 ก่อน ตรวจ 91 หน้าและรอยเขียนให้ครบ หากล้มเหลว ข้อความใหม่จะระบุขั้น/ช่วงหน้าแทนการเดาสาเหตุ

ยังไม่ commit/push งานรอบนี้ และไม่แก้ main branch.

## แก้พาธไฟล์ชั่วคราวและเลขช่วงหน้า — รอบผู้ใช้พบ load-document ล้มเหลว

อ่านเฉพาะ diagnostic metadata ใน OS Temp พบว่างานล้มเหลวขั้น load-document ตั้งแต่ชุดแรก ทั้ง 4/2/1 หน้าและ HTML เพียงประมาณ 243–847 KiB จึงไม่ได้ใช้การลดคุณภาพหรือปรับหน่วยความจำเพื่อแก้รอบนี้

ทำซ้ำด้วยพาธภาษาไทยและอักขระสงวน %/# ได้ ERR_BLOCKED_BY_CLIENT (-20): การเทียบ URL เป็น string บล็อกไฟล์ที่ระบบสร้างเอง และ loadFile ไม่รับประกันการเข้ารหัสอักขระสงวนให้ตรงกับ file URL ของ Node

แก้เฉพาะ runtime electron/pdfExport.cjs และข้อความใน ExportModal.jsx:
- realpath ไฟล์ชั่วคราวแล้วเปิดด้วย loadURL(pathToFileURL(documentPath).href) ซึ่งเป็น URL ของไฟล์สั้น ๆ ไม่ใช่ HTML/data URL ทั้งเล่ม
- ตรวจ file URL โดยถอดรหัสด้วย fileURLToPath และเทียบพาธเฉพาะไฟล์ที่สร้างเอง รวมรูปแบบ canonical/เดิมและตัวพิมพ์บน Windows ปฏิเสธไฟล์อื่น network query/hash และ encoded slash ต่อไป
- ส่ง params ของ exportDialogPdfRange เป็น argument ที่สามของ t ตาม API จริง แสดงเลขหน้าแทน {first}/{last} โดยไม่แก้ระบบแปลภาษาส่วนกลาง

ผล:
- เคสพาธภาษาไทย + %/# ที่ล้มเหลวก่อนแก้ ส่งออก 91 หน้าครบหลังแก้ PDF 6,989,985 bytes ตรวจข้อความไทย ภาพ ลายมือ ลำดับและสัดส่วนหน้า
- ผ่าน OS Temp จริงใต้ชื่อผู้ใช้ Windows พร้อมโฟลเดอร์ย่อยไทย %/# ข้อมูลจำลองล้วน โฟลเดอร์ทดสอบใหม่ถูกล้างหลังปิด Electron โดยตรวจ resolved path ภายใน OS Temp ก่อน recursive delete
- Unit 193 ผ่าน รวม URL แบบ percent encoded/Unicode และปฏิเสธการเข้าถึงไฟล์อื่น
- PDF suite 30 ผ่าน ไม่มี renderer error รวมการกด ExportModal จริงและตรวจเลขช่วงหน้าครบทั้ง en/th/zh/ru
- Build ผ่าน มีคำเตือนขนาด chunk เดิม

โค้ด main process ต้องปิด/เปิด BetterNote เพื่อโหลดใหม่ ยังไม่อ่านหรือส่งออกสมุดจริงของผู้ใช้ และยังไม่ commit/push
