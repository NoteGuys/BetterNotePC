# เฟส 5.4 — PDF พร้อมแสดงขณะเลื่อน

วันที่ 8 ตุลาคม 2026 · ฐาน a1730d9 บน sol-work · งานรอบนี้ยังไม่ commit/push

## ผลที่ผู้ใช้ได้

PDF ที่นำเข้าใหม่มีภาพเล็กพร้อมแสดงทุกหน้าและภาพย่อก่อนการนำเข้าสำเร็จ เมื่อเลื่อนหรือเปลี่ยนหน้า แอปใช้ภาพที่เตรียมไว้ก่อน แล้วสร้างภาพละเอียดเฉพาะหน้าที่อ่านและหน้าใกล้เคียง ไม่ใส่หน้ารอโหลดหรือช่องว่างแทนภาพ PDF ที่มีอยู่ ระหว่างวาดภาพละเอียดมีภาพเดิมอยู่ใต้ Canvas เสมอ

การเลื่อนกลับใช้ภาพละเอียดจากแคช การเลื่อนผ่านยกเลิกคำขอที่ไม่มีผู้ใช้แล้ว คิวให้หน้าแสดงสำคัญกว่างานเตรียมล่วงหน้า และหยุดเริ่มงานระหว่างกดปากกา/ลากวัตถุ/อินพุตค้าง งาน worker ที่รันอยู่หยุดและต่อใหม่เมื่อมี pointerdown ไม่เพิ่ม Canvas ของทั้งสมุด

หากอ่านเนื้อหาหน้าจากฐานข้อมูลไม่สำเร็จ ภาพพร้อมแสดงยังอยู่และมี Retry โดยไม่เปิดให้เขียนลง metadata placeholder จนกว่าจะอ่านหน้าจริงครบ

## ข้อมูลและความคมชัด

- เก็บ PDF ต้นฉบับหนึ่งชุดต่อแหล่ง พร้อม SHA-256 และเลขหน้าต้นฉบับ เก็บภาพ JPEG พร้อมแสดงด้านยาวสูงสุด 960 px และภาพย่อสูงสุด 320 px ทุกหน้า ไม่บันทึกภาพใหญ่ที่สร้างระหว่างอ่านทับข้อมูลโน้ต
- ภาพอ่านละเอียดสร้างเฉพาะเมื่อใช้ และเตรียมบริเวณหน้าปัจจุบัน ±3 ล่วงหน้า; UI Canvas ยังใช้ช่วง/เพดานเฟส 5.2–5.3 เดิม
- worker ที่อ่าน PDF เก็บเอกสารต้นฉบับหนึ่งชุดระหว่างใช้งาน ไม่อ่าน original ซ้ำทุกหน้าเมื่อ digest/สมุด/รอบกู้คืนตรง และคืน worker หลังไม่มีงาน 15 วินาที
- แคชภาพละเอียดใช้เพดาน RAM 32 MiB ร่วมกับแคชภาพย่อ ภาพอ่านไม่เกิน 4 ล้านพิกเซล/ขอบ 4,096 px; ภาพส่งออกและสำรองไม่เกิน 16 ล้านพิกเซล/ขอบ 8,192 px ตาม budget
- สำรอง .bnote/JSON ใช้ข้อมูลที่เซฟพร้อมต้นฉบับ ส่วน PDF สำรอง/PDF ส่งออก/ภาพส่งออกสร้างพื้นหลังละเอียดจากต้นฉบับทีละหน้าและรวมลายมือ ภาพ และข้อความ
- กู้คืน/ลบหน้าเจ้าของต้นฉบับยังใช้การย้ายต้นฉบับเดิมใน transaction ไม่เปลี่ยนระบบซิงค์ ฟังก์ชันบัญชี หรือรูปแบบฐานข้อมูลโน้ต
- การนำเข้าเผยแพร่ notebook/pages พร้อมกันใน transaction เดียวหลังเตรียมภาพครบ ไฟล์เสียหรือ transaction ล้มเหลวไม่เหลือสมุดครึ่งเล่ม
- validator ยืนยันว่าไฟล์สำรองที่ใช้ระบบภาพตามต้องการมีต้นฉบับ เลขหน้า digest และภาพพร้อมแสดงครบก่อนรับเข้า ไม่ขยายเงื่อนไขนี้ไปบังคับ PDF รุ่นเก่าที่มีเฉพาะภาพ

ฟอนต์มาตรฐานและ CMap bundle ในแอปและส่ง URL ที่ resolve แล้วจากหน้าต่างเข้า worker ป้องกัน relative URL ที่ใช้ไม่ได้จาก blob worker ทุกไฟล์ใช้ได้จาก file:// และไม่มี CDN

PDF ที่ใช้ฟิลเตอร์สี/หน้ากาก Luminosity ซึ่ง OffscreenCanvas ไม่รองรับใช้ตัวอ่าน PDF.js แบบ DOM เดิมเพื่อรักษาภาพถูกต้อง แต่ยังนำเข้าภาพเล็กและสร้างภาพใหญ่เฉพาะเมื่อใช้ เส้นทางนี้ไม่ได้ raster ทุกหน้าแบบใหญ่ตอนนำเข้า การเตรียม native ใช้ Canvas/encoding แบบ async และคืน resources แต่ยังทำงานใน renderer จึงไม่รับรองเวลาเฟรมของ PDF พิเศษที่ซับซ้อนทุกไฟล์

## ข้อจำกัดและวิธีตรวจด้วยผู้ใช้

การนำเข้ายังเตรียมภาพเล็กทุกหน้าให้ครบก่อนแจ้งเสร็จ เป็นเวลารอระหว่างนำเข้า PDF ครั้งแรกเพื่อให้การเลื่อนมีภาพพร้อมใช้งาน ภาพที่แสดงแรกอาจคมน้อยกว่าภาพละเอียดเมื่อกระโดดไกลหรือซูมทันที ไม่อ้างว่าไม่มี decode/render delay บนทุกอุปกรณ์หรือไฟล์ทุกขนาด

PDF เก่าที่ไม่มีต้นฉบับใช้ภาพเดิมต่อ ไม่มีการย้าย/เขียนทับข้อมูลผู้ใช้หรือพยายามสร้าง PDF ต้นฉบับคืนจาก JPEG สมุดเก่าที่มีภาพใหญ่จึงยังมีไฟล์สำรองภาพขนาดเดิม

ชุด migration ขณะตรวจรอบนี้มี heartbeat gap สูงสุดประมาณ 576 ms และ long task 116 ms บน fixture ขนาด ~4.7 MB การตรวจความถูกต้องผ่าน แต่ไม่ใช้ยืนยันว่าแอปไม่มี lag ทุกเส้นทางหรือเครื่องทุกชนิด

วิธีลอง: นำเข้า PDF ที่มี 30–60 หน้า รอการนำเข้าเสร็จ เปิดภาพย่อและเลื่อนไปต้น/กลาง/ท้าย เลื่อนกลับ เปิดแนวตั้งแล้วอ่านต่อ เขียนและ Undo สักหน้า ปิดเปิดสมุดใหม่ ส่งออกหน้าเป็น PDF/ภาพ และตรวจการกู้คืนจากสำรองในสมุดทดสอบแยก ภาพต้องไม่หายเป็นช่องว่าง รอยเขียนและพื้นหลังต้องครบ และตำแหน่งหน้าต้องตรงกัน

## สถานะเฟส

งานพัฒนาเฟส 5.1–5.5 และชุดตรวจอัตโนมัติตามขอบเขตเสร็จแล้ว รอผู้ใช้ลองความรู้สึกกับ PDF/อุปกรณ์จริง และเซฟรอบ 5.4 ตามขั้นตอนแสดงไฟล์/ตรวจข้อมูลลับ/รอ “ตกลง” ไม่มี commit/push อัตโนมัติ

## แก้ Export PDF ทั้งเล่มครั้งแรก — 8 ตุลาคม 2026

ผู้ใช้ลองแล้วแจ้งว่าส่วนอื่นผ่าน แต่ PDF ทั้งเล่มล้มเหลว และต้องส่งออกหน้า 1 ก่อน รอบนี้แก้เฉพาะการสร้าง PDF ใน electron/pdfExport.cjs และเพิ่มชุดตรวจที่ใช้ printToPDF จริง

ทำซ้ำด้วยสมุดสังเคราะห์ 91 หน้าที่มีภาพ JPEG ต่างกันทุกหน้า ข้อความ และลายมือ ตั้งแต่โปรเซส Electron ใหม่ คำสั่งแรกเป็นส่งออกทั้งเล่ม: ทางเดิมใช้ data URL ยาว 9,358,984 ตัวอักษรแล้ว loadURL ล้มเหลวด้วย ERR_INVALID_URL ก่อนถึง printToPDF

เปลี่ยนเป็นเขียน HTML ไปไฟล์ชั่วคราวใน temp ของแอปแบบ async โหลดไฟล์นั้นในหน้าต่างส่งออกที่ซ่อน แล้ว printToPDF ตามเดิม ปิด JavaScript และ Node integration ยังคง sandbox และอนุญาตอ่านเฉพาะไฟล์ชั่วคราวของคำสั่งนั้นกับ data images ปฏิเสธเครือข่าย/ไฟล์อื่น ปิดหน้าต่างและล้าง directory ของงานนั้นเมื่อสำเร็จ/ล้มเหลว/timeout และไม่กลืนข้อความ timeout เป็นข้อผิดพลาดทั่วไป

ก่อนหน้านี้การตรวจ native export ใน PDF suite ใช้ตัวรับ IPC จำลองเพื่อดู HTML/ภาพ จึงไม่ได้ตรวจขั้น printToPDF ทั้งเล่มจริง หลักฐานใหม่นี้ใช้ IPC และ printToPDF จริงใน Electron โดยไม่เปิดโปรไฟล์ติดตั้งหรือข้อมูลผู้ใช้

- สมุดรูปแบบเดิม 91 หน้า: PDF จริง 6,706,658 bytes จำนวน 91 หน้า หน้าต้น/46/ท้ายถูกต้อง หน้าแนวตั้ง/นอนตรง พิกเซลพื้นหลังแดงและลายมือสีน้ำเงินตรง
- PDF ที่นำเข้าใหม่ด้วย lazy raster 91 หน้า: PDF จริง 46,139,556 bytes จำนวนหน้า/ลำดับ/ขนาด/พื้นหลัง/ลายมือครบ ทั้งสองชุดเริ่มด้วยโปรเซสใหม่และไม่ได้ส่งออกหน้าเดียวก่อน
- หลังคำสั่งเสร็จไม่มีโฟลเดอร์ betternote-pdf-* ของงานค้างใน QA temp และเหลือหน้าต่าง main เพียงหนึ่งหน้าต่าง
- เพิ่ม unit 4 กรณีสำหรับ temp lifecycle เมื่อสำเร็จ/ล้มเหลว/timeout, URL access และผู้เรียก IPC ที่ไม่ได้รับอนุญาต
- ไม่มีการแก้ระบบภาพย่อ ปากกา ซิงค์หรือฟังก์ชันอื่นในรอบแก้ Export นี้ และยังไม่ commit/push

ให้ปิดแล้วเปิด BetterNote เวอร์ชันทดสอบใหม่เพื่อโหลด main-process handler ใหม่ เปิดสมุดเดิมแล้วกด PDF — entire notebook เป็นการส่งออกครั้งแรก ไม่ต้องส่งออกหน้า 1 ก่อน ทดสอบนี้ยืนยันกรณีที่ทำซ้ำได้ ไม่รับรอง native PDF ทุกไฟล์หรือเครื่องทุกชนิด
